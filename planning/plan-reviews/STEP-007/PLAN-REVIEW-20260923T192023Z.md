- [F-002] medium/evidence — Implementation plan шаг 6 (boundarySpies.ts): фильтр stack по extension.extensionPath. Сценарий: В dev-профиле extensionPath — корень репозитория, префикс путей тестов, mocha, test-cli и VS Code в .vscode-test/, поэтому собственные вызовы тестов и VS Code попадают под фильтр. Влияние: Boundary suite либо ложно падает, либо фильтр ослабят ad hoc, и no-shell/no-mutation доказательство обесценится. Направление исправления: Считать нарушением только кадры с файлом path.join(extensionPath,'dist','extension.js'); показать проверкой, что вызов из test-кода не нарушение, а из bundle — нарушение.
- [F-003] medium/evidence — Implementation plan шаги 6 и 8: spies на vscode.window.createTerminal, tasks.executeTask, authentication.getSession, workspace.fs, applyEdit в packaged-профиле. Сценарий: Extension Host выдаёт отдельный экземпляр vscode API на расширение по пути модуля; в packaged-профиле тесты вне расширения получают другой instance, их патчи не видны bundle. Влияние: Packaged boundary suite даст ложный PASS по terminal/task/auth/fs/applyEdit, хотя Acceptance опирается именно на них. Направление исправления: Контрольный тест перехвата в packaged-профиле (seam, вызывающий spied API из bundle), либо размещение packaged-тестов внутри out/packaged/extension, либо явно заявить и записать в Evidence, что API-граница в packaged доказывается static bundle scan и dev-профилем.
- [F-004] medium/evidence — Implementation plan шаг 5 (watchers без restart). Сценарий: Все пять watcher-сценариев проходят через converge с fallback на harnessNavigator.refresh; сломанный watcher не отличим от рабочего. Влияние: Acceptance «watcher refresh works without Extension Host restart» не доказано; аналогичная дизъюнкция признавалась материальной в review STEP-003 (F-021). Направление исправления: Добавить жёсткий watcher-only assert без fallback минимум для manifest и artifact watcher либо падать, если все сценарии сошлись только через fallback.
