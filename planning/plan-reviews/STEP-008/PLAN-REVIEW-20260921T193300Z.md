## Findings

### F-001 — Портируемая `dev/ino` identity проверка не является эквивалентом containment

**Severity:** high

**Category:** contract

**Location:** `planning/tasks/STEP-008.md` — Implementation plan, F-009 шаги 2 и 3 (и анализ
«Именно этот dev/ino identity check, а не procfs-часть, ловит symlink-swap regression F-008»);
`src/projectModel/manifestService.ts:442-459`.

**Scenario:** План утверждает, что `dev/ino` identity сохраняет F-008 guarantee «на любой
платформе без изменений», и поэтому при `resolveOpenedDescriptorCanonicalPath() === undefined`
(Windows и любая неподдержанная platform) предлагает **не** бросать `ManifestContainmentError`
и полагаться только на identity check. Это неверно: `dev/ino` доказывает лишь, что открытый
descriptor и текущий path указывают на один объект, но не доказывает, что объект находится
внутри `realRoot`. Подменяется не финальный component (его закрывает `O_NOFOLLOW`), а
промежуточный каталог `.harness` в том же TOCTOU-окне, которое уже смоделировано hook-ом
`beforeOpen` (`tests/unit/manifestService.test.ts:247`). Воспроизведено локально на Linux
с текущей последовательностью флагов: opened content = `"SECRET: leaked\n"`,
`dev/ino identity match = true`, `realpathSync('/proc/self/fd/<fd>') = /tmp/out-*/.harness/manifest.yaml`,
`isContained(realRoot, procfsPath) = false`. То есть содержимое вне workspace успешно
прочитано бы, и отклоняет его **только** procfs-ветка, которую план объявляет необязательной.

**Impact:** На платформах без canonical-path re-derivation план даёт строго более слабую
границу workspace, чем текущая Linux-реализация, и при этом сохраняет состояние `valid`.
Это прямо противоречит собственному Acceptance STEP-008 («Существующая Linux
no-follow/containment security-гарантия … не ослаблена ни для одной платформы»), Scope §2
(если эквивалентная fail-safe последовательность недоступна — требуется отдельный,
точно описанный platform-limited typed diagnostic state и явное product/architecture
решение, а не скрытая деградация), Deliverables («кросс-платформенный **или** явно
platform-limited и задокументированный reader») и `docs/architecture.md#security-boundaries`
+ ADR-001 (fail-safe чтение, containment после resolution). Реализация по этому плану не
сможет одновременно удовлетворить Acceptance и Implementation plan.

**Fix direction:** Либо (a) добиться реального containment открытого объекта на каждой
заявленной платформе (например, доказуемая re-derivation canonical path либо fail-safe
последовательность, повторно верифицирующая цепочку каталогов после open, с отказом до
`readSync`), либо (b) осознанно объявить platform-limited подмножество: ввести отдельный
typed diagnostic state с точной причиной («containment проверка недоступна на этой
платформе»), зафиксировать решение в architecture/ADR и, при необходимости,
в `package.json`. Молчаливый downgrade до `dev/ino`-only в текущей формулировке плана
недопустим.

### F-002 — `realpathSync('/dev/fd/<fd>')` не даёт canonical path открытого файла на macOS

**Severity:** high

**Category:** implementation

**Location:** `planning/tasks/STEP-008.md` — Implementation plan, F-009 шаг 1, ветка
`'darwin'` и её обоснование («macOS/BSD предоставляет тот же fd-alias механизм через
`fdescfs`, реализующий идентичную гарантию, что и Linux procfs»).

**Scenario:** На Linux `/proc/self/fd/<fd>` — это magic symlink, и `realpath` возвращает путь
целевого объекта. На macOS записи `/dev/fd/<fd>` предоставляются `fdesc`-механизмом и не
являются symlink на целевой файл: `realpath("/dev/fd/3")` возвращает сам `/dev/fd/3`
(канонический путь открытого файла на macOS получается через `fcntl(F_GETPATH)`, который
Node `fs` не экспонирует; `fdescfs` — терминология FreeBSD, а не доказательство про macOS).
Следовательно `isContained(realRoot, '/dev/fd/3')` вернёт `false`, и
`assertOpenedManifestContained` будет бросать `ManifestContainmentError` для **любого**
корректного manifest на macOS.

**Impact:** Основной дефект F-009 (валидный workspace недостижим вне Linux) остаётся
невыполненным для macOS: состояние остаётся `configurationBlocked` с той же неверной
причиной. Acceptance criterion №1 STEP-008 не достигается. Хуже того, предложенный
unit-тест этого не поймает: на Linux runner `/dev/fd` — symlink на `/proc/self/fd`
(проверено в этом окружении), поэтому вызов `resolveOpenedDescriptorCanonicalPath('darwin', fd)`
вернёт корректный путь и тест станет ложным подтверждением.

**Fix direction:** Не декларировать darwin-эквивалентность без реальной проверки. Либо
подтвердить механизм на настоящем macOS runner (CI job) перед тем, как класть его в
security-critical ветку, либо трактовать macOS так же, как остальные не-Linux платформы,
и решать вопрос через F-001 fix direction. Unit-тест по ветке `'darwin'` на Linux runner
не должен считаться evidence.

### F-003 — Утверждение о доступности `O_NOFOLLOW` на Windows не обосновано, а потеря `O_NONBLOCK` не рассмотрена

**Severity:** medium

**Category:** implementation

**Location:** `planning/tasks/STEP-008.md` — Implementation plan, F-009 шаг 3;
`src/projectModel/manifestService.ts:400-403`.

**Scenario:** План пишет «если `constants.O_NOFOLLOW !== undefined` … покрывает Linux/macOS
и, по данным Node/libuv, обычно Windows тоже». Источник этого «по данным» не приведён, и он
противоречит документированному поведению Node: POSIX-специфичные open-константы
(`O_NOFOLLOW`, `O_NONBLOCK`, `O_DIRECTORY`, `O_NOATIME`, `O_SYNC`) на win32 не
определяются. Кроме того, текущий код собирает флаги через bitwise OR
(`constants.O_RDONLY | constants.O_NONBLOCK | constants.O_NOFOLLOW`), а `x | undefined`
в JS даёт `x | 0` — то есть на Windows уже сегодня беззвучно исчезает и `O_NOFOLLOW`, и
`O_NONBLOCK`, без какого-либо сигнала. План адресует только `O_NOFOLLOW` и вовсе не
упоминает `O_NONBLOCK`, который был введён как guard F-006 (не блокировать Extension Host
на non-regular/FIFO open).

**Impact:** Ключевая посылка Windows-ветки плана («O_NOFOLLOW, скорее всего, есть») ложна,
поэтому фактически на Windows всегда будет исполняться слабый fallback из F-001. Плюс
беззвучная потеря `O_NONBLOCK` — незадокументированная деградация guard-а другого,
ранее закрытого finding.

**Fix direction:** Определять фактические возможности runtime явно (проверять каждую
константу по отдельности, собирать флаги детерминированно и фиксировать результат в
модели состояния), а не через bitwise OR с возможным `undefined`. Итоговый platform
capability должен быть наблюдаем в типизированном состоянии/диагностике, а не
подразумеваться.

### F-004 — «Симулированный `win32`» тест не доказывает Acceptance criterion №1

**Severity:** medium

**Category:** evidence

**Location:** `planning/tasks/STEP-008.md` — Implementation plan, F-009, блок
«Platform-aware tests», последние два пункта; Acceptance criteria №1; Verification.

**Scenario:** План предлагает доказать закрытие F-009 тестом, в котором platform
инъецируется в `assertOpenedManifestContained`. Но решение об open-флагах (шаг 3) ключуется
не на platform, а на `constants.O_NOFOLLOW !== undefined`; на Linux runner эта константа
определена (проверено: `O_NOFOLLOW = 131072`, `O_NONBLOCK = 2048`). Значит «симулированный
`win32`»-прогон всё равно откроет файл с `O_NOFOLLOW|O_NONBLOCK` и пройдёт по пути, который
на настоящем Windows недостижим. План также не описывает, как `platform` попадает из
публичной сигнатуры `detectProject(workspaceRoot, hooks)` через `readBoundedManifest` в
`assertOpenedManifestContained`.

**Impact:** Acceptance «на каждой заявленной поддерживаемой платформе корректный workspace
достигает `valid`» не доказывается заявленной Verification: вся Verification исполняется
только на Linux (что уже зафиксировано в `REVIEW-20260921T184919Z.md`,
`tests_evidence`). Получается тот же класс дефекта, что и в STEP-002: зелёный Linux-прогон
выдаётся за доказательство cross-platform контракта.

**Fix direction:** Либо сузить Acceptance до явно задокументированного platform-limited
подмножества (см. F-001), либо добавить реальный cross-platform прогон (matrix CI на
macOS/Windows) в Verification, либо сделать все platform-зависимые решения (включая набор
open-флагов) параметрами одной инъектируемой capability-структуры, чтобы симуляция
покрывала весь путь, и явно назвать это симуляцией, а не доказательством платформы.

### F-005 — Ручной registry воспроизводит класс дефекта F-010 в обратную сторону

**Severity:** medium

**Category:** implementation

**Location:** `planning/tasks/STEP-008.md` — Implementation plan, F-010 шаги 1-2;
`tests/unit/manifestService.test.ts:100-119`.

**Scenario:** Текущий regex автоматически обнаруживает литералы прямых вызовов
`diagnostic(...)` (его дефект — неполнота по источникам). Предложенный
`PRODUCTION_DIAGNOSTIC_MESSAGES: readonly string[]` — вручную поддерживаемый список: ничто
структурно не заставляет разработчика добавить в него **новый** литерал. После замены
regex на импорт registry сценарий «добавлен новый `diagnostic('X', 'New message.')`, не
внесённый в registry, ключа в bundles нет» пройдёт unit-тест молча, тогда как сегодняшний
regex его бы поймал.

**Impact:** Acceptance «regression test детерминированно падает при удалении любого ключа»
формально выполняется, но исходная причина F-010 (неполнота множества проверяемых keys)
не устраняется структурно, а переносится на дисциплину разработчика. Для STEP, чей
единственный смысл — закрыть F-010, это недостаточно.

**Fix direction:** Сделать registry источником типа, а не просто массивом: объявить
литеральный union из registry и типизировать им параметр `message` у `diagnostic()` и
конструктора `ManifestInputError`, чтобы незарегистрированный литерал отклонялся
`yarn typecheck`. Тогда полнота проверяется компилятором, а unit-тест сверяет registry с
обоими bundles.

### F-006 — Список источников для registry включает нелокализуемые internal messages

**Severity:** low

**Category:** contract

**Location:** `planning/tasks/STEP-008.md` — Implementation plan, F-010 шаг 1
(перечисление `assertRegularManifest`, `readBoundedManifest`,
`assertReliableNoFollowSupport`/её замена, `validateManifest`, `detectProject`);
`src/projectModel/manifestService.ts:433-440,449-458`.

**Scenario:** Сообщения `Reliable no-follow manifest reading is unavailable.` и
`Opened manifest identity is not contained.` принадлежат `ManifestContainmentError`,
никогда не доходят до `diagnostic()` (в `detectProject` они заменяются на
`Manifest resolves outside of the workspace root.`) и отсутствуют в
`l10n/bundle.l10n.json` / `l10n/bundle.l10n.ru.json`. Если включить их в
`PRODUCTION_DIAGNOSTIC_MESSAGES`, новый regression test начнёт требовать ключи, которых

**Impact:** Неоднозначность прямо ведёт либо к падающему тесту, либо к добавлению новых
пользовательских строк, что запрещено Mutation policy («без добавления новых
пользовательских строк сверх уже используемых»).

**Fix direction:** Зафиксировать в плане точный критерий членства в registry: только
литералы, фактически передаваемые в `diagnostic(...)` или в `ManifestInputError` (то есть
попадающие пользователю через `vscode.l10n.t`); internal containment/diagnostic-технические
сообщения остаются вне registry и вне bundles.

## Verdict rationale

BLOCKED.

Формальная часть contract в порядке: Goal/Scope/Out of scope/Mutation policy взаимно
непротиворечивы на уровне границ (никаких новых artifact paths, parsing, command graph, UI),
traceability двусторонняя (REQ-002, REQ-008, Accepted ADR-001 → STEP-008 и обратно),
`architecture_refs` существует, активных canonical Open Questions нет, circular
readiness dependency из audit устранён (`depends_on: [STEP-001]`, `STEP-001` —
`status: completed` с ready plan и PASS review), projections пересобраны
(`sync-projections.py --check` → `PASS`), заявленная Verification соответствует реальным
`package.json → scripts`, планирование свежее (`contextBasis sha256:e5e0b50e…`).
Формулировки Acceptance также корректно выводятся из REQ-002 (типизированные состояния и
containment) и REQ-008 (полная EN/RU локализация diagnostics).

Блокирует не форма, а предложенный технический подход к security-sensitive части.
Ядро F-009-плана построено на утверждении, что портируемая `dev/ino` identity проверка
эквивалентна текущей Linux-гарантии, а procfs-часть — лишь дополнение. Это утверждение
опровергается прямым экспериментом (F-001): подмена промежуточного path component
оставляет `dev/ino` совпадающими, и единственное, что отклоняет чтение внешнего файла, —
именно canonical-path containment. Поэтому шаг «не бросать `ManifestContainmentError`
только из-за отсутствия canonical-path re-derivation» делает границу workspace вне Linux
строго слабее, что прямо противоречит Acceptance criterion №2, Scope §2 и Forbidden-пункту
Mutation policy этого же STEP, а также `docs/architecture.md#security-boundaries` и ADR-001.
Параллельно macOS-ветка опирается на неверное утверждение о `/dev/fd` (F-002), из-за чего
F-009 для macOS остался бы незакрытым, а предложенный unit-тест на Linux runner дал бы
ложное подтверждение; Windows-ветка опирается на необоснованное утверждение о
`O_NOFOLLOW` (F-003) и «доказывается» тестом, который на Linux физически не проходит по
Windows-пути (F-004).

Это не implementation/evidence дефекты, исправимые внутри STEP без изменения контракта:
выбор между «доказуемо кросс-платформенный containment» и «явно задокументированное
platform-limited решение с отдельным typed diagnostic state» — это отсутствующее
product/architecture decision, которого требует сам Scope §2 и которое влияет на ADR/REQ
и, возможно, на `package.json`. Поэтому verdict — `BLOCKED`, а не `FAIL`.

Дополнительно к переработке подлежит F-010-часть: ручной registry закрывает заявленное
Acceptance-условие, но структурно не устраняет причину F-010 (F-005) и содержит
неоднозначность по составу источников (F-006); оба чинятся внутри STEP при повторном
планировании. F-007 — косметический drift, который стоит устранить в том же проходе.

Рекомендация: переработать Implementation plan (явно определить и обосновать платформенную
модель containment, отделить доказуемое от симулируемого в тестах, типизировать registry) и
повторить независимый planning review.
