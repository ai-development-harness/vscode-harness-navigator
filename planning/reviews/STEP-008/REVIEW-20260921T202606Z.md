## Findings

### F-001 — Linux-specific ancestor-race protection (`deriveOpenedPath`) не застрахована ни одним тестом

**Severity:** medium

**Category:** evidence

**Location:** `src/projectModel/manifestService.ts:521-543` (`deriveOpenedPath` ветка
`assertOpenedManifestContained`), `:143-144` (production wiring);
`tests/unit/manifestService.test.ts` (отсутствующее покрытие).

**Scenario:** Acceptance criterion 3 `STEP-008` и `ADR-005` требуют, чтобы защита от гонки
на промежуточном ancestor directory «оставалась действующей на Linux… без изменений в
наблюдаемом поведении». Ни один test в suite не создаёт сценарий, который отличает
`deriveOpenedPath`-проверку от портируемой `dev`/`ino` проверки: все containment-тесты —
либо static symlink (отклоняется ещё до open через `realpathSync`+`isContained`), либо
final-component swap (отклоняется портируемым `dev`/`ino`). Единственная assertion,
трогающая `deriveOpenedPath`, — `typeof linux.deriveOpenedPath === 'function'` на чистой
функции, что не доказывает enforcement. Independent general review воспроизвёл это mutation
testing: замена production wiring на `{ ...resolveManifestOpenCapability(...), deriveOpenedPath: undefined }`
проходит `tsc` (0), `eslint` (0) и все 29 unit tests (29/29) без единого red flag; интеграционный
suite тоже не поймал бы это (4 fixture дают одинаковый observable state).

**Impact:** Единственный platform-specific security control, который `ADR-005` явно обещает
сохранить только на Linux, может быть удалён или обессилен будущим рефакторингом без единого
failing gate — тот же класс дефекта, что и исходный F-008 в `STEP-002`, для портируемой
половины которого тест уже есть, а для Linux-specific половины — нет.

**Fix direction:** Добавить в уже Allowed `tests/unit/manifestService.test.ts` детерминированный
unit test через существующий `beforeOpen` seam: подменить именно **промежуточный** ancestor
(например, `.harness` → symlink на внешний каталог с `manifest.yaml`) и проверить
`configurationBlocked` под реальной (Linux) capability. Independent review подтвердил
сценарий детерминирован: под реальной capability даёт `configurationBlocked`, под
`resolveManifestOpenCapability('win32', {})` — `valid` с содержимым внешнего manifest. Per
`ADR-005`, зеркальный non-Linux assertion писать не нужно.

### F-002 — Статический symlink самого `manifest.yaml` (не configured path) не покрыт тестом ни под одним non-Linux profile

**Severity:** low

**Category:** evidence

**Location:** `src/projectModel/manifestService.ts:129-137` (pre-open `realpathSync` +
`isContained(realRoot, realManifest)`); отсутствующее покрытие в
`tests/unit/manifestService.test.ts`.

**Scenario:** `ADR-005` §1 делает отклонение статического outside-root symlink безусловной
гарантией на любой platform, а Consequences прямо требуют наблюдаемости platform capability
в tests. Ни один test не делает `.harness/manifest.yaml` **самим** static symlink на внешний
файл (существующий test на `:222` покрывает symlink у *configured path*, это другая функция).
Security review подтвердил mutation-ом: удаление pre-open containment check оставляет все 20
module unit tests зелёными, при этом direct probe показывает `valid`+внешний `release` под
win32/darwin-like profile и `configurationBlocked` на реальном Linux (портируемый check там
задублирован procfs-backstop, поэтому Linux-only прогон не поймал бы потерю).

**Impact:** Дефекта сегодня нет (unmutated код блокирует сценарий на всех трёх profile), но
это единственная реализация guarantee #1 `ADR-005` на macOS/Windows, и её потеря не была бы
замечена Linux-only CI.

**Fix direction:** Добавить по одному test на non-Linux profile (переиспользовать
`WINDOWS_LIKE_CAPABILITY` и добавить darwin-shaped capability), проверяющий, что
`.harness/manifest.yaml`-symlink на внешний valid manifest даёт `configurationBlocked` и не
выдаёт внешний `release` через `messageArguments`.

### F-003 — Нет behavioral test под macOS-shaped profile (флаги есть, `deriveOpenedPath` нет)

**Severity:** low

**Category:** evidence

**Location:** `tests/unit/manifestService.test.ts:18,136-162,192-202,331-362`.

**Scenario:** Behavioral tests используют только реальный Linux profile и
`WINDOWS_LIKE_CAPABILITY` (ничего). Комбинация «`O_NOFOLLOW`/`O_NONBLOCK` есть,
`deriveOpenedPath` нет» — буквальный macOS-случай из `ADR-005` — не проверяется
end-to-end; darwin проверен только на уровне чистой функции.

**Impact:** Низкий: final-component swap под этим profile идёт через `ELOOP`-путь к тому же
результату, а F-001/F-002 покрывают смежные ветки отдельно; Acceptance явно требует
behavioral-профиль только для Windows.

**Fix direction:** Если F-001 всё равно правится, добавить darwin-shaped capability
(`{ ...resolveManifestOpenCapability('linux', constants), deriveOpenedPath: undefined }`
с реальными POSIX-константами) в valid-project и final-component-swap кейсы.

### F-004 — `ADR-005 → Security implications` формулирует final-component guarantee строже, чем реально даёт код (hard link case)

**Severity:** low

**Category:** implementation

**Location:** `docs/adr/ADR-005-platform-scoped-manifest-containment.md:120-126` (Security
implications) vs `:56-59` (Decision §1).

**Scenario:** Decision §1 точно говорит про подмену финального component **на symlink**;
Security implications убирает эту оговорку и звучит как безусловная гарантия против «любой
подмены финального component». Security review экспериментально показал: hard link
(`linkSync`) на final component проходит `realpathSync`/`dev`/`ino`/procfs незамеченным на
любой platform (тот же `dev`/`ino` by construction) — `detectProject` возвращает `valid` с
внешним содержимым и на реальной Linux capability, и под win32-like profile.

**Impact:** Наблюдаемое поведение кода не изменилось относительно pre-STEP-008 (Linux-путь
не тронут), риск чисто документационный: будущий читатель может принять формулировку
Security implications за более сильную гарантию, чем решение реально даёт.

**Fix direction:** Привести формулировку Security implications в соответствие с Decision §1
(добавить «на symlink») либо явно отметить hard-link case как часть того же принятого
residual risk. Не production code; вне Mutation policy `STEP-008` для `ADR-005`, если только
review не сочтёт это «фактическим расхождением с реализацией».
