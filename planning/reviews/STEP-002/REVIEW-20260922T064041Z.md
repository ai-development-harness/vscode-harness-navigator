## Findings

### F-012 — Висячий symlink в configured path ошибочно проходит containment

**Severity:** medium

**Category:** implementation

**Location:** `src/projectModel/manifestService.ts:301-329`, особенно `:314-325`; `tests/unit/manifestService.test.ts:241-255`

**Scenario:** Manifest задаёт `sources.requirements: linked-requirements`. Внутри workspace `linked-requirements` является symlink на внешний каталог, который пока не существует. `existsSync(candidate)` возвращает `false` и для отсутствующего пути, и для висячего symlink. Цикл поднимается к существующему workspace ancestor, `realpathSync` проверяет только его, после чего `resolveContainedPath()` возвращает `undefined`, а `detectProject()` — `valid`. Probe на текущей ревизии вывел `{"kind":"valid","category":"ValidHarnessProject"}`. Если внешний target появится после detection, сохранённый configured path остаётся допущенным к будущему чтению за пределами root.

**Impact:** STEP-002 Acceptance, REQ-002 и security boundary architecture требуют блокировать symlink configured path за пределами owning workspace до доступа. Текущая проверка не доказывает containment такого пути; последующий потребитель valid project state может прочитать внешний target. Нынешний unit test покрывает только symlink с уже существующим внешним target.

**Fix direction:** Отличать несуществующий компонент от symlink через `lstat` при поиске ancestor; висячий symlink отклонять как `configurationBlocked` либо безопасно разрешать target и проверять его containment до выдачи `valid`. Добавить regression для висячего final-component symlink и вложенного symlink ancestor; после исправления выполнить новый независимый review.
