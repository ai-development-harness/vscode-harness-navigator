## Findings

### F-009 — Валидный Harness workspace всегда блокируется вне Linux

**Severity:** high

**Category:** implementation

**Location:** `src/projectModel/manifestService.ts:389`,
`src/projectModel/manifestService.ts:432`, `package.json:1`,
`docs/architecture.md:39`

**Scenario:** Пользователь устанавливает опубликованный universal VS Code extension на macOS или
Windows и открывает корректный пустой Harness 0.6.0 workspace. `readBoundedManifest()` всегда
вызывает `assertReliableNoFollowSupport()`, который для любого `process.platform !== 'linux'`
бросает `ManifestContainmentError`. `detectProject()` преобразует его в
`configurationBlocked` с сообщением о якобы выходящем за workspace manifest, поэтому ветка
`valid` недостижима. Package manifest не ограничивает `os`, а project/architecture contracts
описывают обычный VS Code extension на поддерживаемом Node runtime, не Linux-only продукт.

**Impact:** REQ-002 и Acceptance STEP о корректном пустом проекте и Harness 0.6.0+ не выполняются
на двух основных VS Code desktop platforms; диагностическая причина при этом фактически неверна.
Зелёный Linux Extension Host не доказывает распространяемый package contract.

**Fix direction:** Сохранить no-follow/post-open identity guarantee через platform adapter:
использовать доступный `O_NOFOLLOW` и проверку identity/canonical path фактически открытого файла
на каждой поддерживаемой платформе либо реализовать эквивалентную fail-safe последовательность
open/fstat/realpath/stat без чтения до совпадения объекта и containment. Добавить platform-aware
tests; если продукт действительно должен стать Linux-only, сначала требуется отдельное явное
изменение product/architecture contract и package metadata, а не скрытая runtime деградация.

### F-010 — Regression F-007 не охватывает все production localization keys

**Severity:** medium

**Category:** evidence

**Location:** `tests/unit/manifestService.test.ts:100`,
`src/projectModel/manifestService.ts:383`, `src/projectModel/manifestService.ts:405`

**Scenario:** Из EN/RU bundle удаляется `Harness manifest must be a regular file.` либо
`Harness manifest exceeds {0} bytes.`. Тест с названием `production diagnostic keys...` всё равно
проходит: regex извлекает только literal, переданный вторым argument прямого вызова
`diagnostic(...)`, тогда как оба ключа создаются через `new ManifestInputError(...)` и попадают в
`diagnostic()` лишь динамически в catch. Реальный RU integration test наблюдает invalid release,
но не non-regular/oversized path.

**Impact:** Текущее поведение F-007 исправлено ручным совпадением bundles, но заявленное Evidence
о сверке всех production keys неверно, а два из трёх исправленных localization paths могут снова
стать English fallback без падения unit/integration gates. Обязательный test reviewer не может
считать regression proof достаточным.

**Fix direction:** Вынести localization keys этого producer-а в единый типизированный registry
либо проверять все источники messages, включая `ManifestInputError`, без хрупкого partial regex.
Удаление любого production key должно детерминированно ломать unit test; RU Extension Host или
эквивалентный observable test должен покрыть хотя бы одну ветку `ManifestInputError`.
