### F-001 — Runtime localization boundary объявлена, но нигде не подключена

**Severity:** medium
**Category:** implementation
**Location:** `src/extension.ts` (весь файл), `l10n/bundle.l10n.json`, `l10n/bundle.l10n.ru.json`, `package.json#l10n`
**Scenario:** Given STEP-001 объявляет двухслойную локализацию и `package.json` содержит `"l10n": "./l10n"`; When выполнить `grep -rn "l10n" src/`, то единственные совпадения находятся в `tests/unit/localization.test.ts`, а в `src/**` нет ни одного вызова `vscode.l10n.t`; Then ключ `extension.activated.log`, присутствующий в обоих runtime bundles, недостижим из production кода, и runtime-слой локализации не имеет ни одной call site.
**Impact:** Implementation plan шаг 3 требует именно «`l10n/bundle.l10n.json` + `l10n/bundle.l10n.ru.json` с доступом через `vscode.l10n.t` для runtime-строк». Сейчас поставлены только данные без доступа: работоспособность связки `package.json#l10n` → bundle → `vscode.l10n.t` ничем не доказана, а в VSIX упакован мёртвый ключ. Acceptance criterion «Пользовательские strings имеют RU и EN resources с English fallback» выполнен только для manifest-слоя (`package.nls*.json` через `%extension.displayName%`/`%extension.description%`); runtime-половина границы не подтверждена. Следующие STEP унаследуют непроверенную границу локализации.
**Fix direction:** Внутри scope STEP-001 подключить единственную lifecycle-строку через `vscode.l10n.t('extension.activated.log')` (например, в существующий activation-путь, не создавая product-сервисов и не выполняя I/O) и доказать её integration-тестом, либо удалить недостижимый ключ из обоих bundles и явно зафиксировать, что runtime-слой локализации закладывается позже. Смешанное состояние «данные есть, доступа нет» оставлять нельзя.

### F-002 — Тест English fallback тавтологичен: проверяет локальный helper, а не поведение расширения

**Severity:** medium
**Category:** implementation
**Location:** `tests/unit/localization.test.ts:30-44` (`resolveWithEnglishFallback`), используется в тестах на строках 62-80
**Scenario:** Given тест «отсутствующий русский ключ откатывается на английский текст, а не на пустую строку или сырой ключ»; When он исполняется, то он вызывает функцию `resolveWithEnglishFallback`, объявленную в том же тестовом файле, с литералами `{ 'greeting.hello': 'Hello' }` и `{}`; Then утверждение проверяет только сам тестовый helper — ни `src/**`, ни bundles проекта, ни loader VS Code в проверке не участвуют.
**Impact:** Implementation plan шаг 4 прямо запрещает «доказывать поведение только helper-моками вместо реальной активации», а acceptance REQ-010 требует «Проверки не утверждают реализацию только через mocks helpers вместо наблюдаемого поведения». Зелёный результат создаёт ложную уверенность в границе локализации.
**Fix direction:** Заменить тавтологию на проверку наблюдаемого поведения: integration-тест в Extension Host с `--locale ru` (и с ключом, намеренно отсутствующим в `bundle.l10n.ru.json`), утверждающий фактическую строку, которую возвращает `vscode.l10n.t`. Оставшиеся locale-independent unit-проверки (паритет ключей, непустые значения, отсутствие canonical tokens) корректны и сохраняются.

### F-003 — Integration-тест не наблюдает фактическое освобождение registrations

**Severity:** medium
**Category:** implementation
**Location:** `src/test/integration/extension.test.ts:30-54`
**Scenario:** Given plan шаг 4 требует в Extension Host «проверить наблюдаемый результат активации и корректное освобождение registrations»; When тест «deactivate безопасно вызывается и идемпотентен» исполняется, то он выполняет только `assert.doesNotThrow(() => extensionModule.deactivate())` дважды; Then реализация, в которой `deactivate()` не освобождает ни одного disposable (например, если убрать `activeRegistry?.dispose()` и оставить только `activeRegistry = undefined`), прошла бы этот тест без изменений.
**Impact:** Acceptance criterion «Extension корректно активируется и освобождает registrations» в реальном Extension Host не доказан. Освобождение проверено только на unit-уровне изолированного `LifecycleRegistry`, то есть в отрыве от фактической пары `activate`/`deactivate` и от `ExtensionContext.subscriptions`. Регрессия в `src/extension.ts:47-53` не будет поймана ни одним слоем тестов.
**Fix direction:** Сделать disposal наблюдаемым из Extension Host, не раскрывая приватное состояние: например, экспортировать из `src/extension.ts` test-observable счётчик активных registrations (или возвращать его через повторную активацию) и утверждать в integration-тесте переход `count > 0` → `count === 0` после `deactivate()`, а не только отсутствие исключения.

### F-004 — `tests/unit/**/*.ts` не покрыт ни одним tsc project

**Severity:** medium
**Category:** implementation
**Location:** `tsconfig.json` (`include: ["src/**/*.ts"]`, `exclude: ["src/test/**/*"]`), `tsconfig.test.json` (`include: ["src/test/**/*.ts"]`), `package.json#scripts.typecheck`, `package.json#scripts.test:unit`
**Scenario:** Given `yarn typecheck` — это `tsc --noEmit -p tsconfig.json`; When выполнить `tsc --noEmit -p tsconfig.json --listFiles` и `tsc --noEmit -p tsconfig.test.json --listFiles`, то первый включает только `src/extension.ts` и `src/lifecycle/disposableRegistry.ts`, а второй — только `src/test/integration/extension.test.ts`; Then ни один файл `tests/unit/**/*.ts` не компилируется `tsc`, а `yarn test:unit` исполняет их через `tsx`, который стирает типы без проверки. Type error в unit-тестах пройдёт `typecheck`, `lint` и `test` молча.
**Impact:** Acceptance criterion «TypeScript compile работает в strict mode» и plan шаг 1 («strict TypeScript ... с раздельными конфигурациями для source и tests») выполнены лишь частично: unit-слой тестов остаётся непроверяемым типами. `tsconfig.eslint.json` действительно включает `tests/**/*.ts`, но используется только как parser project для type-aware ESLint-правил и никогда не вызывается как `tsc`, поэтому compile-ошибки им не обнаруживаются. Дополнительно `docs/development.md` описывает `yarn typecheck` как проверку «для `src/**/*.ts`», хотя фактически `src/test/**` исключён — документация закрепляет неточную границу.
**Fix direction:** Ввести type-check покрытие unit-слоя реальным `tsc` (расширить `tsconfig.test.json` на `tests/**/*.ts` с соответствующим `rootDir`, либо добавить отдельный noEmit-project и включить его в `yarn typecheck`), после чего привести формулировку в `docs/development.md` в соответствие фактическому покрытию.

### F-007 — Каждый disposable попадает и в реестр, и в `context.subscriptions`, что даёт двойной dispose на штатном пути деактивации

**Severity:** low
**Category:** implementation
**Location:** `src/lifecycle/disposableRegistry.ts:34-38` (`register`), `src/extension.ts:26-33`, `src/extension.ts:47-53`
**Scenario:** Given `register()` добавляет disposable одновременно в `this.disposables` и в `ExtensionContext.subscriptions`; When VS Code штатно деактивирует расширение, то сначала вызывается экспортированный `deactivate()` (который освобождает всё содержимое реестра), а затем host самостоятельно освобождает `context.subscriptions`; Then `dispose()` каждого зарегистрированного объекта вызывается дважды.
**Impact:** Сегодня безопасно, потому что единственный зарегистрированный объект — `vscode.Disposable`, чей `dispose()` идемпотентен по контракту VS Code. Дефект латентный: как только последующие STEP зарегистрируют неидемпотентный disposable (собственный `EventEmitter`, watcher-обёртку, провайдер с внутренним состоянием), двойное освобождение станет источником трудновоспроизводимых ошибок при деактивации, а `LifecycleRegistry.dispose()` проглатывает исключения и скроет симптом.
**Fix direction:** Сохранить единственного владельца disposal: регистрировать в `ExtensionContext.subscriptions` сам реестр (один раз, как `Disposable`), а отдельные disposables отслеживать только внутри реестра. Это сохраняет требование plan шага 3 о проходе через `ExtensionContext.subscriptions` и устраняет двойной вызов.
