### F-002 — `Harness: Set Filter` / `Harness: Clear Filters` спрашивают workspace root, но пишут настройку глобально на весь workspace

**Severity:** medium
**Category:** implementation
**Location:** `src/views/artifactsView.ts:201-214` (`runSetFilter`), `src/views/artifactsView.ts:217-224` (`runClearFilters`), `src/views/artifactsView.ts:226-243` (`pickValidFolder`), чтение — `src/views/artifactsView.ts:158-166` (`readFilter`); contributions — `package.json` `harnessNavigator.artifacts.filter.*` со `scope: "resource"`
**Scenario:** Given multi-root workspace с двумя valid Harness roots `A` и `B`. When пользователь вызывает `Harness: Set Filter`, выбирает в первом Quick Pick root `A`, затем `status` = `blocked`. Then `getConfiguration('harnessNavigator.artifacts', A.uri).update('filter.status', 'blocked', ConfigurationTarget.Workspace)` записывает ключ на уровне workspace (`settings` внутри `.code-workspace`), а не на уровне выбранной folder: `resource` в `getConfiguration` влияет только на чтение/инспекцию и на выбор target по умолчанию, но не на явный `ConfigurationTarget.Workspace`. В результате фильтр применяется и к root `B` — `readFilter(B)` прочитает то же workspace-значение. Выбор root, который команда запросила у пользователя, не влияет ни на что.
**Impact:** Команда обещает per-root поведение, которого нет. Это прямо противоречит остальной части этого же STEP: `ArtifactsTreeDataProvider.readFilter` вызывается per-folder, а дерево при `>1 valid root` специально рендерит workspace folder узлы, чтобы multi-root изоляция оставалась видимой (Implementation plan шаг 4). Пользователь, отфильтровавший один root, молча теряет артефакты второго; при этом видимый Quick Pick подтверждает обратное. Дефект не воспроизводится на существующем fixture, потому что в нём ровно один valid root (`pickValidFolder` в этом случае возвращает folder без Quick Pick), поэтому тесты его не ловят.
**Fix direction:** Привести обещание UI в соответствие с фактическим хранилищем. Минимальный in-scope вариант: убрать выбор root из `runSetFilter`/`runClearFilters` и читать фильтр без resource-scope (`getConfiguration(CONFIG_SECTION)`), явно задокументировав фильтр как workspace-wide; тогда `scope` filter-свойств в `package.json` логичнее сменить на `window`, как у `sortOrder`. Альтернатива (писать `ConfigurationTarget.WorkspaceFolder` для выбранного root) даёт настоящий per-root фильтр, но отклоняется от явного текста Implementation plan шаг 3 («Записывать preferences только через `...update(..., ConfigurationTarget.Workspace)`») и потому требует отдельного согласования плана, а не тихой правки в FIX.

### F-003 — Сортировка по priority теряет заявленный total order на prototype-именах в untrusted frontmatter

**Severity:** medium
**Category:** implementation
**Location:** `src/views/artifactViewModel.ts:48-51` (`PRIORITY_RANK` через `Object.fromEntries`), использование — `src/views/artifactViewModel.ts:126-132`
**Scenario:** Given STEP-артефакт, у которого в frontmatter `priority: toString` (или `valueOf`, `constructor`, `hasOwnProperty` — любое имя из `Object.prototype`). When активен sort order `priority` и вызывается `sortArtifacts(artifacts, 'priority')`. Then `PRIORITY_RANK['toString']` возвращает унаследованную функцию, а не `undefined`, поэтому `?? UNKNOWN_PRIORITY_RANK` не срабатывает и `leftRank - rightRank` даёт `NaN`; comparator возвращает `NaN`, и `Array.prototype.sort` получает несогласованный comparator. Проверено напрямую: `R['toString'] ?? 4` → `[Function: toString]`, разность → `NaN`.
**Impact:** Нарушается ровно то свойство, которое Implementation plan шаг 2 требует явно: «для неизвестного/отсутствующего поля задать стабильный tail-порядок, чтобы сортировка оставалась total и воспроизводимой». Существующий unit test `sortArtifacts по priority ...` использует значение `'unknown-value'`, которое не попадает в prototype chain, поэтому даёт ложную уверенность в покрытии этого контракта.
**Fix direction:** Строить lookup без прототипа (`Object.assign(Object.create(null), ...)`) либо использовать `Map`/`Object.hasOwn(PRIORITY_RANK, key)` перед чтением. Добавить в `tests/unit/artifactViewModel.test.ts` кейс с `priority: 'toString'`, который проверяет tail-позицию и воспроизводимость порядка.

- Дубликаты ID не приводят к коллизии `TreeItem.id`: `ArtifactIndex` дедуплицирует по `byId` и выдаёт `DuplicateArtifactId` diagnostic, поэтому `snapshot().artifacts` не содержит двух артефактов с одним ID.

Ограничения доказательств: multi-root (`>1 valid root`) поведение tree providers и copy-команды не наблюдались в работающем Extension Host — соответствующие выводы (F-002, F-006a) сделаны чтением кода и рассуждением о семантике `ConfigurationTarget.Workspace`, а не запуском сценария.

## Verdict rationale

Реализация по существу соответствует Scope, Mutation policy, Out of scope, ADR-004 и явным `architecture_refs`; Acceptance criteria достижимы и в основном продемонстрированы реальным Extension Host сценарием, planning context свежий и подтверждён `plan-context`, обязательный `tests` reviewer выполнен и вернул PASS. Поэтому оснований для `BLOCKED` нет: contract-противоречия, невыполнимого acceptance, отсутствующего решения/prerequisite или stale planning context не обнаружено.

Вместе с тем material findings есть, и все они относятся к категориям `evidence`/`implementation` и исправимы внутри текущего STEP через `STEP FIX`: F-001 (Evidence даёт доказуемо неверную причину блокера, из-за чего два deterministic gate остаются красными вместо одной механической регенерации проекций), F-002 (Quick Pick обещает per-root фильтр, которого запись на уровне workspace не даёт, что противоречит per-root чтению и видимой multi-root изоляции этого же STEP), F-003 (заявленный в плане total/воспроизводимый порядок сортировки по priority нарушается на untrusted frontmatter), F-004/F-005 (локализационный и settings-гигиенический дефекты пользовательского уровня), F-006 (непокрытые поведения, поднятые обязательным test reviewer). Наличие material findings исключает PASS, поэтому verdict — **fail**.
