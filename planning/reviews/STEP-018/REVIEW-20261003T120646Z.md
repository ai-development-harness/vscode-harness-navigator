### F-001 — Refresh открытого WebView повторно запускает API для unsupported root

**Severity:** medium
**Category:** implementation
**Location:** src/projectGraph/dependencyGraphPanel.ts:133
**Scenario:** Given В trusted root с поддерживаемым Harness уже открыт Dependency Graph; затем manifest меняется на release ниже 0.10.3 или становится invalid, и owning watcher/Refresh устанавливает blockRoot(unsupportedHarness/unavailable). / When Пользователь нажимает Refresh в оставшемся открытым WebView. / Then DependencyGraphPanel.handleMessage напрямую вызывает ProjectGraphService.refresh; provider проверяет только Workspace Trust, снова запускает Python и может заменить unsupported error на ready graph.
**Expected:** REQ-002, первый Acceptance criterion STEP-018 и ADR-008 разрешают Project State invocation/graph только для valid Harness 0.10.3+; unsupported release должен сохранять localized unsupported state без graph behavior.
**Observed:** Проверка valid state существует в global Harness: Refresh и command opening, но отсутствует у WebView refresh. Read-only reproduction исполнил actual panel handler, production service и настоящий fixed Python entry point fixture: before=error/unsupportedHarness, after=ready, nodes=5.
**Impact:** Обычная смена manifest с последующим нажатием Refresh обходит minimum-version/configuration blocker и возобновляет graph/process behavior для неподдерживаемого root.
**Fix direction:** Проверять актуальную eligibility owning root перед каждым graph invocation, включая WebView refresh и отложенный refresh, через существующий ProjectStateService integration boundary. Для invalid/unsupported root сохранять blocker и не запускать process; добавить regression перехода valid → unsupported/invalid → WebView refresh.
**Fingerprint:** sha256:b14bb66b5a453507d19fe4c9b1befc5aa06e67f36c55664c7fb624680728ae6a

**Admissible alternatives:**
- Передать panel безопасный owning-layer refresh callback, который выполняет re-detect/valid-state check, либо внедрить eligibility callback в graph provider для всех entry points.

**Constraints:**
- Сохранить fixed non-shell invocation и запрет legacy/fallback.
- Не менять canonical lifecycle/API semantics Harness и существующую ArtifactIndex navigation.

**Evidence:**
- src/projectGraph/dependencyGraphPanel.ts:131-135: refresh напрямую вызывает graphs.refresh(this.folder).
- src/projectGraph/projectStateService.ts:48-66: единственный eligibility check перед process — options.isTrusted().
- src/extension.ts:144-158,309-325: global refresh и watcher создают unsupportedHarness/unavailable blocker, который panel refresh перезаписывает.
- Read-only node --import tsx heredoc, exit 0: actual DependencyGraphPanel.prototype.handleMessage + ProjectGraphService + src/test/fixtures/mvp/mvp-valid/.harness/tools/project-state.py вывели {before:error,error:unsupportedHarness,after:ready,nodes:5}.
- docs/requirements/REQ-002-project-detection-and-compatibility.md Acceptance; docs/adr/ADR-008-project-state-graph-integration.md Decision; planning/tasks/STEP-018.md Acceptance criterion 1.

### F-002 — Направление canonical relation скрыто под target node

**Severity:** medium
**Category:** implementation
**Location:** src/projectGraph/dependencyGraphWebview.ts:77
**Scenario:** Given Project State API содержит два STEP и направленное relation STEP-A → STEP-B с depends_on; используется обычная light/dark theme с непрозрачным editorWidget-background. / When Production WebView draw() рисует edge и затем nodes. / Then marker-end находится в центре target node и перекрывается его rect; пользователь видит линию и relation type без читаемого направления.
**Expected:** Graph и STEP dependencies mode должны представлять canonical source/target relations API так, чтобы отличать зависимость A от B от зависимости B от A.
**Observed:** Edge проходит от центра source к центру target, после чего непрозрачные node rect рисуются поверх. Production script reproduction дал path M 150 82.5 Q 300 47.5 390 82.5, target bounds [300,50,490,115], marker endpoint [390,82.5], endpointInsideTarget=true, targetPaintedAfterEdge=true. Details related list также показывает только neighbor ID и relation type, без source/target direction.
**Impact:** Направление depends_on и остальных directed relations недоступно в основном graph UI; противоположные dependencies выглядят одинаково, что мешает навигации и пониманию зависимостей.
**Fix direction:** Завершать directed edge на видимой границе target node либо размещать marker вне перекрываемой области. Добавить production renderer regression, который проверяет видимость arrow endpoint и различимость opposite directions; можно дополнительно показывать inbound/outbound direction в details.
**Fingerprint:** sha256:dae0c1af1bb32bcd12bff644688f6cc843601d150710c8b03080171724cd9c32

**Admissible alternatives:**
- Использовать явную видимую source → target подпись relation при сохранении API direction; визуальные стрелки должны оставаться читаемыми.

**Constraints:**
- Не вычислять новые dependencies и не синтезировать reciprocal edges.
- Сохранить theme variables и API-provided source/target/provenance.

**Evidence:**
- src/projectGraph/dependencyGraphWebview.ts:77: bx=b.x+90, by=b.y+b.height/2; marker-end=url(#arrow); nodes.forEach следует после edges.forEach.
- src/projectGraph/dependencyGraphWebview.ts:57: node rect использует fill:var(--vscode-editorWidget-background).
- src/projectGraph/dependencyGraphWebview.ts:76: related list не обозначает inbound/outbound.
- Read-only node --import tsx heredoc, exit 0: именно shipped dependencyGraphHtml script в VM/DOM adapter вывел endpointInsideTarget=true и targetPaintedAfterEdge=true для двух STEP с depends_on.
- docs/requirements/REQ-011-project-state-dependency-graph.md:26-28; planning/tasks/STEP-018.md Acceptance criterion 4.

**Fix direction:** Согласовать mapping и ProjectDiagnosticCategory с ProjectStatePythonUnavailable из REQ-008; проверить через minimal missingPython → localized panel/Show Diagnostics regression в EN/RU.
**Fingerprint:** sha256:a623dbdd15f4682030b733af74b448cc16e1b86c61c3a3910a1ef0ffee785b84

**Evidence:**

- Read-only rg -n ProjectStatePythonUnavailable|PythonUnavailable по src/tests/REQ-008: требуемый identifier найден только в REQ, production использует PythonUnavailable.

### F-004 — Не доказана RU/EN локализация большинства отказов Project State API

**Severity:** medium
**Category:** evidence
**Location:** src/test/integration/mvp/dependencyGraph.test.ts:27
**Scenario:** Given Project State API возвращает missingTool, missingPython, timeout, oversizedOutput или processError в RU Extension Host. / When DependencyGraphPanel отображает error через PROJECT_STATE_ERROR_MESSAGES. / Then Пользователь видит соответствующее русское локализованное сообщение, а диагностика сохраняет корректную taxonomy category.
**Expected:** REQ-011 требует локализованного Project State error для каждого перечисленного API failure и RU/EN Extension Host coverage; REQ-008 требует локализации errors и стабильной taxonomy.
**Observed:** Реальные unit process tests проверяют только reason codes. Проверка l10n проверяет GRAPH_LABELS, но исключает PROJECT_STATE_ERROR_MESSAGES. Production Extension Host assertion локализации есть только для untrusted; BLOCKED/future-schema/malformed проверяются лишь как error/nodes без текста, а missing tool/Python, timeout, oversized output и process error не проходят through panel в RU/EN.
**Impact:** Явно требуемое STEP-018/REQ-011 автоматизированное доказательство localized process-failure handling и Show Diagnostics taxonomy в EN/RU отсутствует. Неверные переводы не утверждаются: все 13 текущих error keys имеются в обоих bundles; отсутствие этого Host proof уже позволило пропустить фактический mismatch missingPython taxonomy.
**Fix direction:** Добавить минимальные parameterized tests: unit-проверку присутствия всех значений PROJECT_STATE_ERROR_MESSAGES в EN/RU bundles и production Extension Host seam для representative process failures с assertion panel error и Show Diagnostics taxonomy в EN и RU.
**Fingerprint:** sha256:45c1a13d72d13a7f951f652ef544681592e57d4cf7fe2d60c9de9f1629d8ce35
